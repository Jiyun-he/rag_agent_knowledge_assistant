# MyBatis 检索评测结果

## 实验条件

| 项 | 说明 |
|---|---|
| 语料 | MyBatis 3.5.19 官方中文文档 8 篇（`dataset/mybatis-3.5.19-zh/`），约 12.4 万字 |
| 评测集 | 26 个 EvalCase，覆盖语义型、关键词敏感型、代码块型、表格型与跨 chunk 型问题 |
| 知识库 | 两个独立知识空间，同一语料分别用两种切分策略导入 |
| 检索参数 | `topK=5`，`candidateK=20` |
| 回答生成 | 关闭（`enableAnswerGeneration=false`）——本轮只评测检索质量，不引入 LLM 抽样差异 |
| 指标 | Recall@K、Hit@K、MRR、Average Latency（引用类指标因未生成回答而为 NULL） |
| Embedding | `text-embedding-3-small`（1536 维） |
| Reranker | `BAAI/bge-reranker-v2-m3`，本地 CPU 部署 |

Ground truth（每题的期望 chunkId）由人工标注，两套切分分别标注，标注文件见 `annotation/mybatis_26_questions_chunk_ids_updated.xlsx`。

## 两组切分参数

| 策略 | 长度参数 | 重叠 | 产出 chunk 数 |
|---|---|---|---:|
| `FIXED_SIZE` | `max-size=500` 字符（硬上限） | 80 字符 | 298 |
| `STRUCTURE_AWARE` | `target-size=800` / `hard-limit=1200` token | 150 token | 353 |

> 两种策略的计数单位不同：`FIXED_SIZE` 按**字符**计数（`String.length()`），`STRUCTURE_AWARE` 按 **token** 计数（jtokkit，`cl100k_base` 编码，与 `text-embedding-3-small` 的切词一致）。800 与 500 不可直接按数值比较。本语料实测约 **1 个汉字 ≈ 1 个 token**（32,332 个汉字 → 31,604 token，`cl100k_base`），故两者量级接近。

结构感知切分按 Markdown AST 的标题、段落、代码块、表格边界切分，并在每个 chunk 开头带上完整的标题路径（如 `# 配置` + `## 属性（properties）`）。

## 一、分块策略对比

| 模式 | Recall@K 定长 → 结构 | Hit@K 定长 → 结构 | MRR 定长 → 结构 |
|---|---|---|---|
| VECTOR_ONLY | 0.8045 → **0.8301** (+0.026) | 0.9231 → **0.9615** (+0.038) | **0.7917** → 0.7590 (−0.033) |
| KEYWORD_ONLY | **0.7500** → 0.7308 (−0.019) | **0.9231** → 0.8846 (−0.038) | 0.5910 → **0.7532** (+0.162) |
| HYBRID | 0.7917 → **0.8349** (+0.043) | 0.9615 → 0.9615 (±0) | 0.8186 → **0.8346** (+0.016) |
| HYBRID_RERANK | **0.9647** → 0.9503 (−0.014) | 1.0000 → 1.0000 (±0) | 0.9051 → **0.9658** (+0.061) |

### 解读

**结构感知切分在召回类指标上更优，尤其在 HYBRID 模式。** HYBRID 的 Recall@K 提升 0.043（0.7917 → 0.8349），这是最贴近实际使用的模式，说明按语义边界切分让向量召回更容易命中完整答案。VECTOR_ONLY 也同向提升（+0.026）。

**结构感知切分显著改善排序质量（MRR）。** 三个模式的 MRR 都上升，其中 HYBRID_RERANK 提升 0.061（0.9051 → 0.9658），KEYWORD_ONLY 提升 0.162。原因在于结构感知切分在每个 chunk 开头附加了标题路径，使 chunk 自带上下文，排序时更容易把真正相关的内容排到前面。

**KEYWORD_ONLY 出现分化，是本次最值得注意的现象。** 它的 MRR 大幅提升（+0.162），但 Recall 与 Hit@K 反而下降（−0.019 / −0.038）。原因是结构感知切分产出的 chunk 更多、更细（353 vs 298），单个问题对应的期望 chunk 可能被拆到多个 chunk 中，关键词召回的覆盖面因此变窄；但标题路径的加入让命中的那个 chunk 更容易排到前列。

**HYBRID_RERANK 的 Recall 略微下降（−0.014）但不影响可用性**，其 Hit@K 在两套切分下都达到 1.0000，MRR 反而提升到 0.9658，是两种切分下综合表现最好的模式。

**结论**：结构感知切分在本语料与评测集上整体占优，主要体现在召回覆盖与排序质量；代价是 chunk 数增加约 18%，且对纯关键词检索的召回广度有轻微负面影响。

## 二、检索策略对比

### 定长切分下

| 模式 | Recall@K | Hit@K | MRR | 平均延迟 |
|---|---:|---:|---:|---:|
| VECTOR_ONLY | 0.8045 | 0.9231 | 0.7917 | 1137 ms |
| KEYWORD_ONLY | 0.7500 | 0.9231 | **0.5910** | **74 ms** |
| HYBRID | 0.7917 | 0.9615 | 0.8186 | 1470 ms |
| HYBRID_RERANK | **0.9647** | **1.0000** | **0.9051** | 29177 ms |

### 结构感知切分下

| 模式 | Recall@K | Hit@K | MRR | 平均延迟 |
|---|---:|---:|---:|---:|
| VECTOR_ONLY | 0.8301 | 0.9615 | 0.7590 | 1025 ms |
| KEYWORD_ONLY | 0.7308 | 0.8846 | 0.7532 | **24 ms** |
| HYBRID | 0.8349 | 0.9615 | 0.8346 | 960 ms |
| HYBRID_RERANK | **0.9503** | **1.0000** | **0.9658** | 57180 ms |

### 解读

**向量检索是更强的单一基线。** VECTOR_ONLY 在两种切分下的 Recall@K 都高于 KEYWORD_ONLY（+0.055 / +0.099）。这与语料性质有关：26 题中多数是语义型提问，而关键词检索依赖字面匹配，只在类名、属性名这类精确查询上有优势。

**关键词检索的优势在延迟，且差距极大。** KEYWORD_ONLY 平均 24–74 ms，比向量检索快 15–43 倍，比开启重排的 HYBRID_RERANK（2383 倍）快三个数量级。对延迟敏感、且查询含精确术语的场景，它是合算的选择。

**HYBRID 融合的收益不稳定。** 定长切分下 HYBRID 的 Recall（0.7917）反而低于 VECTOR_ONLY（0.8045）；结构切分下则略高（0.8349 vs 0.8301）。它的主要贡献在排序：两种切分下 MRR 都优于 VECTOR_ONLY。这说明等权 RRF 融合能改善名次质量，但不必然提升召回覆盖。

**HYBRID_RERANK 是效果最好的模式，代价是延迟。** 两种切分下 Hit@K 均为 1.0000、MRR 最高（0.9051 / 0.9658）、Recall@K 也处于高位。但 CPU 部署的 reranker 使平均延迟达到 29–57 秒——本实验的 reranker 为本地 CPU 推理（`bge-reranker-v2-m3`），每个 case 需重排 30 个候选，单次约 30 秒。生产环境使用 GPU 推理可大幅降低该开销。

**策略选择建议**：对质量优先的场景选 HYBRID_RERANK；对延迟优先的场景选 KEYWORD_ONLY；需要平衡时 HYBRID 是较稳妥的折中。

## 三、局限

- **样本量 26 题**，结论具备方向性参考价值，但不适合做小幅差异的强断言。
- **评测集由项目自身方法论构建**，问题分布偏语义理解型，对关键词检索不完全公平。
- **reranker 为 CPU 部署**，延迟数字反映的是本地硬件条件，不可直接外推到生产环境。
- **未评测回答质量**：本轮关闭了回答生成，`Citation Precision/Recall` 与 `Grounded` 均为 NULL。回答类指标需要另跑一批开启回答生成的实验。
- 两套切分的 chunk 数量不同（298 vs 353），Recall@K 的分母因此不完全可比，解读时需注意。

## 复现方式

1. 按 `dataset/mybatis-3.5.19-zh/README.md` 准备语料
2. 建两个知识空间，分别以 `rag.chunk.strategy=FIXED_SIZE` 与 `STRUCTURE_AWARE` 导入 8 篇文档，等待索引完成（文档状态 ACTIVE）
3. 从各空间导出 chunk（含全局唯一 `id`），人工标注每题的期望 chunkId
4. 创建 EvalDataset 与 EvalCase，分别对两个数据集运行四种检索模式的 EvalRun
5. 通过 `POST /api/rag/eval/runs/compare` 对比结果
